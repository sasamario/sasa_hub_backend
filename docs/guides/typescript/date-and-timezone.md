# 日付・タイムゾーンの扱い(汎用知識)

「日本時間(JST)で指定された日付を、UTCで保存しているDBと正しく比較する」ために
必要な考え方をまとめる。`GET /api/github/summary`の`from`/`to`パラメータ実装時の議論より。

参考: [MDN - Date](https://developer.mozilla.org/ja/docs/Web/JavaScript/Reference/Global_Objects/Date) /
[ISO 8601(Wikipedia)](https://ja.wikipedia.org/wiki/ISO_8601)

## 大前提: 時刻はコンピュータの中では「1つの数値」でしかない

人間は「2026年8月15日 0時0分0秒」のように年月日で時刻を表現するが、
コンピュータの内部では**ある基準の瞬間から何ミリ秒経過したか、という1つの整数**として
時刻を扱っている。

- 基準点 = **1970-01-01T00:00:00(UTC)**。これを「エポック(epoch)」と呼ぶ
- そこから何ミリ秒経過したか、という数値が**エポックミリ秒(epoch ms)**
- JSの`Date`オブジェクトは、この整数1つを内部に持っているだけ(`date.getTime()`で取り出せる)
- 「年月日」「時刻」「JST」「UTC」といった概念は、**この1つの数値を人間が読める形に
  変換して表示するとき**にだけ登場する。`Date`自体には「これはJSTで作った/UTCで作った」
  という情報は残らない。世界のどこでも共通の「その一瞬」を指す数値が1つあるだけ

## 落とし穴: 時刻を省略した日付文字列は「UTCの0時」として解釈される

```ts
new Date('2026-08-15'); // ← 一見「日本時間の8/15 0時」のつもりでも…
```

ISO 8601の仕様上、**時刻・タイムゾーンを省略した日付のみの文字列はUTCとして解釈される**。
つまり上記は「UTCの2026-08-15 0時」であり、日本時間に換算すると**8/15の朝9時**になってしまう
(UTC+9時間がJSTのため)。「日本時間の0時のつもり」と実際の値が9時間ズレる。

## 対処法: タイムゾーンのオフセットを明示する

```ts
new Date('2026-08-15T00:00:00+09:00');
```

| 部分 | 意味 |
| --- | --- |
| `T` | 日付部分と時刻部分の区切り(ISO 8601の決まりごと) |
| `00:00:00` | その日の0時0分0秒 |
| `+09:00` | 「UTCより9時間進んでいる」というタイムゾーンのオフセット。JST(日本時間)を明示する |

こう書くことで「これは日本時間の0時です」と正しく伝わり、内部的には正しいエポックms
(UTC基準では前日の15時)に変換される。

## DB(Prisma/Postgres)との比較で意識すべきこと

本プロジェクトのPrismaスキーマでは`DateTime`型を素朴な`timestamp`(タイムゾーン情報を
持たない型)としてPostgresに保存している。それでも比較が壊れない理由は以下の通り。

1. `Date`はJSTで作ろうとUTCで作ろうと、最終的には同じ「エポックms」という1つの数値になる
2. Prisma/Postgresへの保存・比較は、常にこのエポックms(をUTC表記に変換したもの)で行われる
3. 保存されている値も、比較条件として渡す値も**同じ土台(エポックms)**の上にあるため、
   DB側にタイムゾーン情報が無くても矛盾なく比較できる

つまり「JST/UTCの解釈」が必要なのは**文字列→`Date`に変換する入り口の一瞬だけ**であり、
そこさえ正しく変換すれば、以降はPrismaもPostgresもタイムゾーンを意識せず、
ただの数値として比較しているだけ、という理解でよい。

逆に言うと、**この入り口(`+09:00`の付け忘れなど)を間違えると、以降のどの層でも
気づく手立てがなく、静かに9時間ズレたデータになる**ので注意が必要。

## 期間の終端(`to`)を「その日を含む」形にする

`from`/`to`で期間を指定する場合、`to`に指定した日付「当日」のデータも含めたいことが多い。
時刻を持つ`activityDate`カラムと比較する以上、`to`の日付をそのまま`lte`で使うと
その日の0時以降のデータが範囲外になってしまう(`to`の0時 = その日の最初の瞬間でしかないため)。

対処法として、**「翌日の0時」を計算し、`lt`(未満)で比較する**とシンプルに解決できる。

```ts
function parseJstDateExclusiveEnd(dateStr: string): Date {
  const date = new Date(`${dateStr}T00:00:00+09:00`);
  date.setUTCDate(date.getUTCDate() + 1); // 翌日のJST 0時に進める
  return date;
}
```

`setUTCDate`でエポックms相当の値に1日分足しているだけなので、タイムゾーンの解釈が
ズレる心配はない(サマータイム等が絡まない単純な加算)。

## 本プロジェクトでの実装方針

- `from`/`to`のような「JSTの日付文字列⇄UTCのDate」変換処理は、特定のドメイン
  (GitHub/Qiitaなど)に依存しない汎用処理のため、`src/common/date.util.ts`に
  独立した関数として置く(クラスに属さないためDIも`@Injectable()`も不要)。
- `parseJstDateStart(dateStr)`: 範囲の開始(その日のJST 0時をUTCのDateに変換)
- `parseJstDateExclusiveEnd(dateStr)`: 範囲の終了(翌日のJST 0時。`lt`で使う前提)
